# usage-habit-report

A local store of token usage from AI coding harnesses. `scan` reads the
harness logs into SQLite and `query` reports on them. Claude Code, Codex
and Antigravity are supported.

No response text is stored. Session names retain the first line of the opening
prompt and, where available, the headline already generated by the harness.
Both titles are limited to 120 characters. The opening prompt is also read
once at ingest to pick a task label (see
[Task labels](#task-labels)); only the label is kept.

## Build

```sh
cargo build --release
./target/release/usage-habit-report --help
```

## Locations

| What   | Path                                          |
|--------|-----------------------------------------------|
| Store  | `~/.local/share/usage-habit-report/usage.db`  |
| Config | `~/.config/usage-habit-report/`               |
| Rates  | `~/.config/usage-habit-report/rates.json`     |

`XDG_DATA_HOME` and `XDG_CONFIG_HOME` override the parent directories.
`USAGE_HABIT_REPORT_CONFIG` overrides the application `config.toml` file.
`--db <path>` (or `USAGE_HABIT_REPORT_DB`) points every command at a
different store. `--offline` (or `USAGE_HABIT_REPORT_OFFLINE=1`) stops every
command from fetching model rates; see [Pricing](#pricing).

`--no-scan` skips the catch-up that every `query` command starts with. The
catch-up is the incremental scan, the enrich step and the price step, so a
query never reports stale data. It prints one `scan: N files read, ...` line
to stderr only when it read something, so `--json` output on stdout stays
clean. With nothing new to read it costs about 0.05 s on a store of 79,000
requests and 1,700 sessions. With `--no-scan` a query reads the store as it is.

JSON shapes of every `query` command are frozen in
[docs/json-shapes.md](docs/json-shapes.md).

## Session headlines

Each scan refreshes session headlines without re-reading unchanged transcripts.
Headlines use existing local metadata, with no model calls. Whitespace is
collapsed and titles are trimmed to 120 characters. The original opening line
remains in `sessions.title` and JSON `title`.

| Source | Default location | Title field |
|--------|------------------|-------------|
| Codex | `~/.codex/state_*.sqlite`, highest numeric suffix | `threads.name`, then `threads.title` |
| Codex fallback | `~/.codex/session_index.jsonl` | `thread_name` by `id` |
| Antigravity | `~/.gemini/antigravity/conversation_summaries.db` | `title` by `conversation_id` |
| T3 | Existing configured state databases | Stored `t3_title` |
| Opening prompt | Existing transcript sources | Stored first-line `title` |

A hand-set title (`usage-habit-report title`) wins over everything.
Codex `name` wins over the index; an index headline wins over the weak SQLite
`title`. Both `name` and index headlines use `codex-name` provenance. Harness
headlines win over T3 titles, then the opening line is used.
Claude Code keeps its opening line unless a T3 title is available. The JSON
`title_source` values are `manual`, `codex-name`, `codex-title`,
`antigravity-summary`, `t3`, and `first-line`. A session without any title has a null `display_title`
and `first-line` provenance. Private session lists and fan-outs use the display
headline. Public snapshots omit all titles.

All title databases are opened with `mode=ro&immutable=1`. Missing, unreadable,
or incompatible sources produce one aggregate note in scan output. Codex's
index also supplies headlines when the SQLite schema changes.

Optional source paths live in `~/.config/usage-habit-report/config.toml`, under
`[sources]`. These are quoted scalar paths, either double-quoted with JSON
escapes or single-quoted literally. Comments may follow a path. `~/` expands
to the home directory. `XDG_CONFIG_HOME` changes the configuration root.
The existing transcript CLI flags remain available; `--codex-dir` supplies
the default state directory and index path when these settings are absent.

```toml
[sources]
codex_state_dir = '/home/demo/.codex'
codex_session_index = '/home/demo/.codex/session_index.jsonl'
antigravity_summaries = '/home/demo/.gemini/antigravity/conversation_summaries.db'
```

## Commands

### `scan`

```sh
usage-habit-report scan [--claude-dir ~/.claude/projects] [--codex-dir ~/.codex] [--antigravity-dir DIR]... [--t3-state FILE]...
```

Reads every log file from the byte offset where the previous scan stopped,
up to the last complete line, in one transaction per file. A partial last
line is left for the next scan. A file smaller than its stored offset is
re-read from byte 0 after its old rows are dropped. Output:

```
claude-code: 120 files seen, 120 files read, 250000000 bytes read, 5000 rows added, 120 sessions added
codex: 900 files seen, 900 files read, 3000000000 bytes read, 40000 rows added, 890 sessions added, 300 repeated token_count events skipped
antigravity: 48 databases seen, 48 databases read, 175000000 bytes read, 8800 rows added, 48 sessions added
enrich: 1480 sessions given a project (0 from a T3 directory), 11 without a directory; t3: 2 databases read, 417 sessions linked; 0.01 s
elapsed: 4.50 s
priced: 61500 rows checked, 61000 with an estimated cost, 500 without a price
```

Each tool line ends with counts of anything unusual it skipped or corrected;
the Codex ones are explained under [Codex ingest](#codex-ingest).

A second scan over unchanged logs reports `0 files read, 0 bytes read`
(`0 databases read` for Antigravity). Antigravity databases are read whole
when they change; see [Antigravity ingest](#antigravity-ingest).
After reading, `scan` runs the enrich step (see
[Projects and T3](#projects-and-t3)) and then the price step (see
[Pricing](#pricing)).

### `query summary`

```sh
usage-habit-report query summary [--json] [--since 12h|7d|2w] [--group-by tool-model|label]
```

Token totals grouped by tool and canonical model (the default; raw variants such as `gemini-3.8-flash-n` fold into `gemini-3.8-flash`, see `query models`), or by task label with
`--group-by label` (see [Grouped by label](#grouped-by-label)). `--since` keeps requests whose
timestamp falls within the last N hours (`h`), days (`d`), or weeks (`w`).
Without `--json` it prints a table whose `est. cost` column is the estimated
cost in USD; a `*` marks a figure that leaves out requests with no price.

JSON shape:

```json
{
  "generated_at": "2026-10-20T04:10:00Z",
  "since": "2026-10-13T04:10:00Z",
  "rates_fetched_at": "2026-10-20T04:19:17Z",
  "totals": {
    "requests": 5000,
    "input_tokens": 25000,
    "cache_read_input_tokens": 480000000,
    "cache_creation_input_tokens": 19000000,
    "output_tokens": 4900000,
    "estimated_cost_usd": 412.37,
    "unpriced_requests": 0
  },
  "groups": [
    {
      "tool": "claude-code",
      "model": "claude-example-model",
      "requests": 3600,
      "input_tokens": 7500,
      "cache_read_input_tokens": 370000000,
      "cache_creation_input_tokens": 12000000,
      "output_tokens": 3000000,
      "estimated_cost_usd": 301.55,
      "unpriced_requests": 0
    }
  ]
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `generated_at` | string | RFC 3339 UTC time the summary was computed |
| `since` | string or null | RFC 3339 UTC lower bound from `--since`; null means all time |
| `rates_fetched_at` | string | RFC 3339 UTC time the prices in use were fetched from LiteLLM |
| `totals` | object | Sum over all groups |
| `groups[]` | array | One entry per (tool, model), ordered by tool, then total tokens descending |
| `tool` | string | `claude-code`, `codex` or `antigravity` |
| `model` | string or null | Raw model name from the log; null when the log has none |
| `requests` | integer | Billed model calls |
| `input_tokens` | integer | Uncached input tokens |
| `cache_read_input_tokens` | integer | Input tokens read from the prompt cache |
| `cache_creation_input_tokens` | integer | Input tokens written to the prompt cache |
| `output_tokens` | integer | Output tokens (includes thinking / reasoning) |
| `estimated_cost_usd` | number or null | Estimated USD at list prices, summed over requests that have a price; null when none do |
| `unpriced_requests` | integer | Requests left out of `estimated_cost_usd` because their model has no price |

Subagent requests are included in the totals of the model that served them.
To separate them, use `requests.is_subagent` or `sessions.parent_session_id`
in the store (see [Antigravity ingest](#antigravity-ingest) for an example).

#### Grouped by label

`query summary --group-by label` returns the same JSON with a different
`groups[]`: one entry per (label, tool), ordered by label, then total tokens
descending, with `label` in place of `model`. The top level also carries
`"group_by": "label"`. A subagent's requests count under its parent session's
label. Requests from sessions with no label are grouped under `unlabelled`.

```json
{
  "generated_at": "2026-10-20T04:10:00Z",
  "since": null,
  "rates_fetched_at": "2026-10-20T04:19:17Z",
  "group_by": "label",
  "totals": { "requests": 5000, "input_tokens": 25000, "...": 0 },
  "groups": [
    { "label": "coding", "tool": "claude-code", "requests": 2500, "input_tokens": 10678,
      "cache_read_input_tokens": 235203786, "cache_creation_input_tokens": 8905200,
      "output_tokens": 2537681, "estimated_cost_usd": 119.79, "unpriced_requests": 0 }
  ]
}
```

### `query labels`

```sh
usage-habit-report query labels [--json]
```

Sessions and token totals per task label, all time. JSON shape:

```json
{
  "generated_at": "2026-10-20T04:10:00Z",
  "totals": { "requests": 5000, "...": 0 },
  "labels": [
    { "label": "coding", "sessions": 100, "manual_sessions": 2, "subagent_sessions": 88,
      "requests": 10124, "input_tokens": 51223222, "cache_read_input_tokens": 0,
      "cache_creation_input_tokens": 0, "output_tokens": 5412940,
      "estimated_cost_usd": 454.37, "unpriced_requests": 0 }
  ]
}
```

`sessions` counts top-level sessions with that label, `manual_sessions` the
ones labelled by hand, and `subagent_sessions` the subagent sessions that
inherit it. The token fields are the same as in `query summary` and cover the
top-level sessions and their subagents. `labels[]` is ordered by `requests`
descending. `unlabelled` appears when a session has no label.

### `query value`

```sh
usage-habit-report query value [--json]
```

Estimates what each subscription buys, from the rate-limit readings the
harnesses leave in their logs, live readings taken by `limits record`, and
the estimated API cost of the same requests. One block per tool, always all
three. Text output opens with plain-language findings, then the figures:

```
- Last 28 days: the 3 plans ($190 a month) carried est. $5,097 a month at API list prices, 26.8x their price. claude-code has only 10 days of history.
- codex drift: 5-hour window, 2026-05 to 2026-10: est. $27 to $10 (-63 %), tokens 25.2M to 52.5M (+108 %). At gpt-6.1-sol rates throughout: $8 to $10 (+25 %), so it holds more work. ...

codex: ChatGPT Plus at $20.00/month; limit readings: readings; reference model gpt-6.1-sol
  session window (5 h): 21.7M tokens, 1.2M uncached+output, 233 requests, 8.2 sessions, est. $13.42 per full window, from 10 of 143 runs
    runs range $10.58 to $15.69, median $13.28
    2026-10: 45 runs, 52.6M tokens, est. $9.96 per full window, $10.44 at reference rates, mostly gpt-6.1-sol (86 %)
    windows used 229, exhausted 33, mean peak 44 %, mid-window resets 11
  2026-10 (partial): est. $338.03 = 16.7x of the price, on pace for $478.65
  mean over 4 complete months: est. $451.12 = 22.0x the price
  pace over the last 28 days: est. $493.37 a month = 24.7x the price
```

**Windows.** Each tool has a session window of 5 hours and a weekly window
of 168 hours, plus any per-model pool the provider reports live (Claude's
Fable weekly pool; Antigravity's Gemini, Argon, and Claude & GPT pools). A
pool covers only the models whose names carry its word. A *run* is a stretch
of rising `used_percent` readings inside one window. It ends at a drop, a
changed reset time, or a gap longer than the window, so mid-window resets
and reset credits start a new run instead of inflating one. Concurrent
sessions interleave their readings, so a lower share against the same reset
time, or an earlier reset time, is skipped as stale. A run stops at its first
reading of its highest share: requests made while a window sits at 100 % are
paid with credits or refused, not covered by the plan. The tool's requests
inside the run are summed (tokens, uncached input plus output, requests,
distinct sessions, estimated cost) and scaled by `100 / rise` to a whole
window. Runs rising less than 20 % are ignored; the ten largest rises are
averaged into `per_window`, with their `spread` (lowest, median, highest).
A window that was never seen exhausted reports the busiest sliding window of
that length as a lower bound instead.

**Drift.** `drift` repeats the mean for every qualifying run by the month it
started, with the month's main model by cost. Each figure is also priced at
one reference model's rates throughout (`reference_cost_usd`; the costliest
model of the last 28 days), which separates a change in how much work a
window holds from a change in model prices.

**Utilization.** Per window, `utilization` counts closed windows, how many
reached 100 %, how many a reset ended early, and the mean peak of the windows
that ran to their reset time, overall and by month. A mid-window reset is a
fall in the share with a later reset time.

**Credits.** Codex readings carry the credit balance (v11). `credits` tracks
what was added and spent, how much went on requests made while a window read
100 %, and how much on mid-window resets. Credit-funded requests are left out
of each month's `multiple` and of the pace.

**Sources.** Codex rollouts carry `rate_limits` on every `token_count`
event (both windows, since late May 2026), so Codex gets a real series.
Claude Code transcripts only record a rejection (`rate_limit_info` with
`status: rejected`) with the window's reset time, so each Claude run spans
`resets_at - 5 h` to the first refusal and is an exact 0 to 100 % reading.
Antigravity logs no limit data. Live readings from `limits record` fill both
gaps from the day sampling starts.

**Months and pace.** `months[]` lists estimated API cost per local calendar
month against the plan price (`multiple`), the days of history in the month,
and for a partial month its cost at that pace over a whole month. `complete`
is false for the current month and the first month seen;
`mean_monthly_cost_usd` and `mean_multiple` average the complete months, or
the partial ones when no month is complete. `pace` is the monthly cost at the
rate of the last 28 days (or of the whole history, when shorter); `combined`
adds the plans together.

Plan prices default to Claude Team at a premium seat ($150), ChatGPT Plus
($20, the plan behind Codex) and Google AI Pro ($19.99, the plan behind
Antigravity). Override them in `config.toml`:

```toml
[subscriptions]
codex = 200 "ChatGPT Pro"   # price a month, optional quoted plan name
claude-code = 150
antigravity = none 'Free tier'   # none: no price, so no multiple
```

JSON shape: see [docs/json-shapes.md](docs/json-shapes.md#query-value).

### `limits record`

```sh
usage-habit-report limits record [--every SECS] [--from FILE]
```

Runs `ai-usage --json claude codex antigravity` and stores the used share,
reset time, and pool of every 5-hour and weekly window in `live_limits`. One
reading prints one line, such as `limits: 10 readings at
2026-10-23T01:25:12Z (antigravity 5, claude-code 3, codex 2)`. `--every`
keeps sampling until interrupted (at least every 30 seconds) and reports a
failed sample on stderr without stopping. `--from` reads saved `ai-usage`
output instead. Set `USAGE_HABIT_REPORT_AI_USAGE` to the binary's path when
`ai-usage` is not on `PATH`.

Claude Code and Antigravity leave no usable limit series in their logs, so a
schedule of these samples is what lets `query value` measure their windows.
Every ten minutes is enough to catch each rise. A launchd agent on macOS,
`~/Library/LaunchAgents/local.usage-habit-report.limits.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>local.usage-habit-report.limits</string>
  <key>ProgramArguments</key><array>
    <string>/Users/you/.cargo/bin/usage-habit-report</string>
    <string>--no-scan</string><string>limits</string><string>record</string>
  </array>
  <key>EnvironmentVariables</key><dict>
    <key>USAGE_HABIT_REPORT_AI_USAGE</key><string>/usr/local/bin/ai-usage</string>
  </dict>
  <key>StartInterval</key><integer>600</integer>
</dict></plist>
```

Load it with `launchctl load ~/Library/LaunchAgents/local.usage-habit-report.limits.plist`.
With cron: `*/10 * * * * usage-habit-report --no-scan limits record`.
`rebuild` keeps `live_limits`, since no log can recreate it.

### `query agents`

```sh
usage-habit-report query agents [--json] [--since 12h|7d|2w]
```

How subagents are used: how many a session spawns, which models and efforts
they run, how many run at once, and the share of tokens they spend. It reads
the store only (no scan, no price step) and runs in well under a second.
With `--since`, only requests in the window count, and a session is counted
if it or one of its subagents has a request in it.

Definitions:

- A subagent belongs to its root: the nearest ancestor that is not a subagent
  (Codex can spawn subagents from subagents). `subagent_count` counts every
  subagent in the tree.
- Tokens are `input_tokens + output_tokens` (uncached input plus output).
  Cache reads and writes are left out.
- `max_concurrent_fanout` is the largest number of a session's subagents whose
  `[first request, last request]` intervals overlap at one instant. Intervals
  are closed, so subagents that touch at one instant overlap there. A subagent
  with no requests has no interval and adds to `subagent_count` only.

JSON shape (abridged):

```json
{
  "generated_at": "2026-10-20T04:10:00Z",
  "since": null,
  "coverage": {
    "antigravity": { "supported": true, "note": "..." },
    "claude-code": { "supported": true, "note": "..." },
    "codex":       { "supported": true, "note": "..." }
  },
  "totals": {
    "top_level_sessions": 672,
    "sessions_with_subagents": 234,
    "subagent_sessions": 820,
    "unlinked_subagent_sessions": 8
  },
  "subagent_token_share": { "subagent_tokens": 43679871, "total_tokens": 375956423, "share": 0.116 },
  "histogram": [
    { "bucket": "0", "min": 0, "max": 0, "sessions": 438 },
    { "bucket": "3-4", "min": 3, "max": 4, "sessions": 45 },
    { "bucket": "20+", "min": 20, "max": null, "sessions": 4 }
  ],
  "by_tool": [
    { "tool": "claude-code", "top_level_sessions": 89, "sessions_with_subagents": 27,
      "subagent_sessions": 225, "unlinked_subagent_sessions": 0,
      "subagent_tokens": 0, "total_tokens": 0, "subagent_token_share": 0.484 }
  ],
  "model_mix": {
    "main_thread": [ { "model": "claude-example-model", "requests": 6534, "tokens": 0, "request_share": 0.122 } ],
    "subagent":    [ { "model": "claude-example-model", "requests": 3305, "tokens": 0, "request_share": 0.297 } ]
  },
  "subagent_efforts": [ { "effort": "high", "requests": 120 }, { "effort": null, "requests": 900 } ],
  "heaviest_fanouts": [
    { "tool": "claude-code", "session_id": "...", "title": "...",
      "subagent_count": 41, "max_concurrent_fanout": 12,
      "subagent_models": [ { "model": "claude-example-model", "requests": 300 } ],
      "subagent_efforts": [ { "effort": null, "requests": 300 } ],
      "subagent_tokens": 1986107, "total_tokens": 2500000, "subagent_token_share": 0.79 }
  ]
}
```

| Field | Meaning |
|-------|---------|
| `coverage.<tool>.supported` | Whether that tool's logs link subagents to a parent session |
| `coverage.<tool>.note` | What is and is not linked |
| `totals.unlinked_subagent_sessions` | Subagent sessions whose parent chain does not reach a top-level session; left out of per-session metrics |
| `subagent_token_share` | Over all requests in the window, including unlinked subagents; `share` is null when there are no tokens |
| `histogram[]` | Top-level sessions by number of subagents; buckets `0`, `1`, `2`, `3-4`, `5-9`, `10-19`, `20+` (`max` null for the last) |
| `by_tool[]` | The same counts per tool, with `subagent_token_share` per tool |
| `model_mix` | Requests and tokens by model, main-thread sessions against subagent sessions; ordered by requests |
| `subagent_efforts[]` | Subagent requests by reasoning effort; `effort: null` means the log has none |
| `heaviest_fanouts[]` | Up to ten sessions, by `max_concurrent_fanout`, then `subagent_count`, then `subagent_tokens` |
| `heaviest_fanouts[].subagent_models[]` | Distinct models the session's subagents ran, with request counts |
| `heaviest_fanouts[].subagent_token_share` | `subagent_tokens / total_tokens` for the session; null when it has no tokens |

Coverage today: Claude Code and Antigravity link every child to its parent.
Codex links `thread_spawn` subagents; a few subagent sessions have no parent
id and are counted as unlinked. Internal `guardian` sessions and
`codex-auto-review` requests are excluded by design. They contribute no sessions,
requests, events, active time, model entries, subagent counts, or fan-out.
Source cursors are kept so excluded rollouts are not re-read. Migration v8
removes stored guardian sessions, requests, and events and refreshes cached
ancestor active time. Manual labels survive.

### `label`

```sh
usage-habit-report label <session-id-or-prefix> <kind>
```

Sets a session's task label by hand. `kind` is one of `research`, `coding`,
`debugging`, `writing`, `review`, `data-analysis`, `ops-config`, `other`. The
session is found by exact id or a unique id prefix across all tools;
an ambiguous prefix is refused and lists the candidates. Subagent sessions
cannot be labelled: they take their parent's label. The hand-set label is
kept in its own table, so later scans and a rebuild of the raw-log rows do
not change it.

### `title`

```sh
usage-habit-report title <session-id-or-prefix> "<title>"
```

Sets a session's display title by hand, for the private dashboard and
`query session`. The session is found as for `label`. Whitespace is collapsed
and the title is cut at 120 characters. The title is kept in its own table
(`session_titles`); the headline refresh copies it into `display_title` with
`manual` provenance and never replaces it, and a rebuild keeps it. The
original opening line stays in `title`. Public snapshots omit all titles, so a
hand-set title never reaches the published pages.

### `query untitled`

```sh
usage-habit-report query untitled [--json]
```

Lists the sessions highlighted on any dashboard page (heaviest fan-outs,
longest, costliest, for every window and tool page) whose title is still the
opening prompt: `title_source` of `first-line` or `codex-title`. It reuses
the page queries, so it tracks what a reader can see as sessions age in and
out of the windows. `--json` adds the raw log path, the readable transcript
(for Antigravity, the harness's `brain/<id>/.system_generated/logs/
transcript.jsonl` when present) and the pages. The `/summarize-sessions`
skill in `~/.claude/skills` reads this list, has a model summarize each
transcript, and sets the results with `title`; run it by hand whenever the
dashboard shows raw opening lines.

### `rebuild`

```sh
usage-habit-report rebuild [same options as scan]
```

Deletes the rows read from raw logs (`sources`, `sessions`, `requests`,
`codex_cursors`), then scans, enriches and prices everything again. Hand-set
labels (`session_labels`) and `rates.json` are kept. Usage whose raw logs
have been deleted since is lost, so rebuild only to recover from a parser
fix or a damaged store. Output is the `scan` output, then
`rebuild elapsed: ...`.

### `query session` and `query thread`

```sh
usage-habit-report query session <key> [--json] [--rows] [--since 12h|7d|2w]
usage-habit-report query thread <t3-thread-id> [--json] [--rows] [--since 12h|7d|2w]
```

One session: tool, session id, title, project, T3 thread id and title, task
label (hand-set preferred), models with request counts, start, end and
elapsed time, request count, the four token kinds plus reasoning tokens,
estimated cost (null when no request has a price; `unpriced_requests` counts
those left out), and the subagent summary (count, models, efforts, token
share, maximum fan-out; the same definitions as `query agents`). `--rows`
adds one row per request (time, model, effort, tokens, cost). Prompt and
response text never appear. The title line uses the refreshed display headline;
a separate `first line` shows the original opening line. JSON `title` retains
the opening line, with additive `display_title` and `title_source` fields.

`session` matches `<key>` as an exact session id, then an exact T3 thread
id, then a session-id prefix, and the first stage with any match decides.
`thread` matches only the T3 thread id. Several matches exit with code 2 and
list the candidates (stdout: JSON error body with `--json`, a table
otherwise); no match exits with 1. Both conventions are the same as for
`query project`. Field names and types are in
[docs/json-shapes.md](docs/json-shapes.md).

### `query models`

```sh
usage-habit-report query models [--json]
```

One line per (tool, raw model name): the canonical name, the LiteLLM key it
priced against, `priced` yes/no, and the request count. Unpriced names sort
first, so a name the canonical table does not cover shows up at the top.
JSON is an array of `{tool, model, canonical_model, litellm_key, priced,
requests}`.

### `query project`


### `rates update` and `rates apply`

```sh
usage-habit-report rates update        # fetch LiteLLM prices, re-price every request
usage-habit-report rates apply [--all] # price requests without a cost (every request with --all)
```

`rates update` fails when the fetch fails; it never falls back.

## Pricing

Every request row gets `canonical_model` and `cost_usd`. All dollar figures
are estimates at public list prices: no batch, priority, flex, regional, or
subscription pricing.

**Rates.** Prices come from LiteLLM's
[`model_prices_and_context_window.json`](https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json).
`rates.json` keeps the entries whose `litellm_provider` is `anthropic`,
`openai`, `gemini` (Google AI Studio, `gemini/…` keys), or
`vertex_ai-language-models` (bare `gemini-…` keys) and whose `mode` is
`chat`, `responses`, or `completion`. Re-hosted copies (Bedrock, Azure,
Vertex AI Anthropic, OpenRouter, …) are left out. Each entry keeps
`litellm_provider`, `mode`, `input_cost_per_token`, `output_cost_per_token`,
`cache_read_input_token_cost`, `cache_creation_input_token_cost`,
`cache_creation_input_token_cost_above_1hr`, and the tiered
`<field>_above_<N>k_tokens` variants. The file is
`{"fetched_at", "source", "models": {<litellm key>: {...}}}`.

**Refresh.** A command that needs prices (`scan`, `query summary`,
`query models`, `rates apply`) first checks `rates.json`. When the file is
missing, unreadable, or its `fetched_at` is more than 7 days old, it prints
`refreshing model rates from LiteLLM…` on stderr and fetches (10 s timeout).
`--offline` skips the fetch. When the fetch fails, the command notes it on
stderr and uses the old `rates.json`, or, without one, the snapshot compiled
into the binary (`src/rates_snapshot.json`, a `rates update` output
committed to the repository). Refresh never happens in the background.

**Canonical names** (`src/models.rs`). Raw names are lowercased; provider
prefixes (`models/`, `anthropic/`, `gemini/`, …) and Vertex `@` pins are
dropped; enum-style names are rewritten (`claude_v5_opus_thinking` ->
`claude-opus-5`, `MODEL_CLAUDE_4_5_SONNET_THINKING` -> `claude-sonnet-4-5`);
snapshot dates (`-20251001`, `-2025-08-07`) and effort or mode suffixes
(`-high`, `-medium`, `-low`, `-thinking`, `-tiered`, and for Gemini `-n` and
`-trial`) are stripped. `max`
is stripped only from Claude names, since `gpt-5.1-codex-max` is its own
model. Opaque placeholders (`MODEL_PLACEHOLDER_M26`) get no canonical name.
The LiteLLM key is the canonical name, except Gemini, which tries
`gemini/<name>`, `<name>`, then the `-preview` forms of both.

**Cost per request.**

```
cost = input × input_rate + cache_read × cache_read_rate
     + cache_creation × cache_creation_rate + output × output_rate
```

- `input` is uncached input only. Each harness ingester stores it that way.
- Output already includes reasoning tokens (Anthropic and OpenAI count them
  in output; ingesters store `output_tokens` the same way for every tool).
  `reasoning_tokens` is never added again.
- Tiered rates (`_above_200k_tokens`, `_above_272k_tokens`, …) apply to every
  token of a request whose prompt (uncached + cache-read + cache-write input)
  exceeds the threshold. Rates a tier does not list stay at the base rate.
- Cache writes use the 5-minute rate. The 1-hour rate is never used: no
  harness records the TTL of a cache write.
- A missing cache-read or cache-write rate falls back to the input rate.
- A model with no LiteLLM entry, or no input or output rate, gets
  `cost_usd = NULL`. No default rate is ever used.

**Price step.** After `scan`, and in every command that needs prices, rows
with a null `canonical_model` or `cost_usd` are priced. After `rates update`,
or when the command just refreshed the rates, every row is re-priced. A
trigger clears `canonical_model` and `cost_usd` whenever a later merge
changes a row's model or token counts, so a row priced mid-stream is priced
again with its final counts.

## Projects and T3

The enrich step runs after every `scan` and refreshes project assignments
for stored sessions. Unchanged assignments are not rewritten. To reindex
projects without rereading raw logs or changing stored requests, run:

```sh
usage-habit-report reindex
```

`reindex --t3-state FILE` uses a specific T3 database and can be repeated.
Reindexing preserves usage whose raw logs have been deleted.

**Project.** A session's project is derived from its recorded `cwd`:

- Inside a git repository: the repository's toplevel, found by walking up to
  the nearest directory holding `.git`. When `.git` is a file (a linked
  worktree), its `gitdir:` folder's `commondir` leads to the main
  repository's `.git`, and the main repository's toplevel is the project, so
  every worktree of a repository is one project. A `.git` file without
  `commondir` (a submodule) or whose common dir is not a `.git` folder (a
  worktree of a bare repository) leaves that directory as its own project.
- Outside a repository: the directory itself.
- A directory that no longer exists: the `cwd` string as recorded, except
  that a path containing `/.claude/worktrees/<name>` or
  `/.git/worktrees/<name>` (a deleted worktree) resolves as the path before
  that marker, through the rules above when that repository still exists.
  Sessions already filed under such a path are resolved again by the next
  enrich.

Existing directories are canonicalized first (symlinks resolved, so `/tmp/x`
becomes `/private/tmp/x` on macOS). `sessions.project` holds the path and
`sessions.project_name` its last component. Each distinct `cwd` is resolved
once per run. A previously established project is retained when its recorded
working directory has disappeared and no current ownership rule applies.

T3's recorded worktree paths map to their parent workspace roots, including
worktrees that have been deleted. These mappings apply to every session
under that path, including native subagents without a T3 session link.
Paths with conflicting owners within a T3 database are skipped.

For an umbrella project outside Git, add a path mapping to `config.toml`:

```toml
[project_aliases]
"/work/arena" = "/work/arena"
"/work/old-checkout" = "/work/main-repository"
```

Each source path and its descendants belong to the target project. A
self-mapping groups nested runs, judging directories, and embedded repositories
under one umbrella. Paths must be absolute and cannot be `/`. The most specific
source path wins; configured mappings override T3 mappings for the same source.
Targets resolve through the Git rules above; aliases do not chain.
A mapping for `/work/arena` does not match `/work/arena-other`.
The next scan or `reindex` applies changed mappings to historical sessions.
Shared container directories such as `/work` are not inferred as projects.

**T3.** T3 Code keeps a state database at `~/.t3/userdata/state.sqlite` (and
`~/.t3-personal/userdata/state.sqlite` for a second profile).
`--t3-state FILE` (repeatable) replaces both; a path that does not exist is
skipped silently, so `--t3-state /nonexistent` turns the step off. Each
database is opened with `immutable=1`, read-only, and never written. One that
fails to open or read gets one `notice:` line on stderr and is skipped;
nothing else changes.

- `provider_session_runtime.resume_cursor_json` names the harness session:
  `{"threadId": "<codex session id>"}` for `codex` rows,
  `{"schemaVersion": 1, "sessionId": "<conversation id>"}` for `antigravity`
  rows. Other providers are ignored; Claude Code sessions get no T3 link.
- `sessions.t3_thread_id` is the row's `thread_id` and `sessions.t3_title`
  the `projection_threads.title`. A later scan refreshes the title of a
  session already linked to the same thread. When a session appears in more
  than one database, the first database in the list wins.
- A session with no recorded `cwd` uses the thread's `worktree_path`, else
  its project's `projection_projects.workspace_root`, for project resolution.
  Recorded worktree ownership then folds that path into the parent project.
  That directory is not written to `cwd`.

**Session keys.** `query::resolve_session(key)` finds a session by exact
`session_id`, then exact `t3_thread_id`, then `session_id` prefix; the first
stage with a match decides, and several matches at that stage are reported
as ambiguous.

## Claude Code ingest

- Source: every `*.jsonl` under `~/.claude/projects`, at any depth.
- `<project>/<uuid>.jsonl` is a session whose id is the file stem.
- `<project>/<parent-uuid>/subagents/agent-<id>.jsonl` is a subagent
  transcript. Its session id is the file stem (`agent-<id>`). It gets
  `is_subagent = 1` and `parent_session_id = <parent-uuid>`, the folder name,
  which matches the `sessionId` field inside its records. `agent_type` comes
  from the sibling `agent-<id>.meta.json`.
- Requests come from `assistant` records with `message.usage`. Claude Code
  writes one record per content block and repeats the usage each time, with
  the output count growing during streaming. Rows are therefore keyed by
  `message.id`, and repeated records merge by taking the maximum of each count.
- Assistant records with model `<synthetic>` are skipped. Claude Code
  generates these locally (errors, interrupts); they are not API calls.
- User turns and the title skip tool results, `isMeta` and compact-summary
  records, and content that starts with `<local-command`, `<command-name`,
  `<command-message`, or `<task-notification`.
- `cwd` is the first non-empty `cwd` field seen. Start and end times are the
  earliest and latest record timestamps.
- Lines that fail to parse are counted and reported by `scan`, then skipped.

### `serve`

```sh
usage-habit-report serve [--port 7878] [--no-open] [--no-publish]
```

Opens the dashboard: one page rendered from the store on
`http://127.0.0.1:<port>/`. The server only ever binds the loopback address;
`--port 0` takes a free port, and the URL is printed first on stdout. The
browser opens unless `--no-open` is given. The store is opened read-only on
every request, so a scan in another terminal shows up on reload and the
dashboard never prices or migrates anything after the optional startup publish step.

The page shows an activity map of local-time hour by weekday, shaded by
uncached input plus output tokens, with a window of 1 week, 4 weeks (default),
12 weeks, or all time (`?window=1w|4w|12w|all`) and an optional tool filter
(`?tool=claude-code|codex|antigravity`). Hovering or focusing a cell shows
its exact figures. The window totals under the map are the same figures as
`query summary --since 4w` (or `1w`, `12w`, or no `--since`) for the same window.
Below the map and totals, every panel follows the same window and tool
filter, states its window, and names any tool with no requests in it:

- **Model by task kind**: one radar chart per canonical model in a
  three-column grid. Each axis shows the percentage of that model's requests
  assigned to a task kind. Models are grouped by provider. Claude models use
  Fable, Opus, Sonnet, Haiku order within the newest major generation, followed
  by older generations. OpenAI uses Astra, Sol, Terra, Luna order, and Google
  uses Argon, Pro, Flash order, with newer major generations first and newer
  minor versions first within each tier. Each chart scales its largest topic to the
  outer ring; the ring ticks and axis labels keep their actual request
  percentages. Small screens show two columns or one. Every model gets
  a chart, including the table's folded long tail. Expand the request-count
  table for the exact figures and stepped shading. `unlabelled` appears only
  when some request in the window has no label. Column totals equal the
  per-label totals of `query summary --group-by label` for the window.
- **How much of my work I hand to subagents**: rows of 20 squares, each
  5 % of tokens, filled by the subagent share. "By tool" has one row per
  tool plus all tools, with sessions that spawned subagents out of all
  top-level sessions, from `query agents --since <window>` (with a tool
  filter, that tool's `by_tool` row). "By month" covers all history from
  `requests.is_subagent`, the last twelve local calendar months. The private
  dashboard adds the ten heaviest fan-outs and each tool's coverage note.
- **Time and cost by project**: the ten costliest projects with sessions,
  tokens and cost from `query projects`, active time (the sum of each
  top-level session's `active_seconds` as `query session` reports it), and
  the tool mix by requests. The full path is in the name's tooltip.
- **Longest and costliest sessions**: top eight top-level sessions by
  active time and by estimated cost, titled by `sessions.title` (the stored
  first line of the opening prompt); figures match `query session <id>
  --since <window>`.
- **Cache-read ratio**: per tool, cache reads over all input (uncached, cache
  read, cache write), from the window totals.
- **Spend by week** (by month for all time): estimated cost per tool, weeks
  counted back from now so they tile the window; each column adds up to the
  window total. The public page titles it "What my use would cost at API
  prices" and leaves out the estimated API cost table, the sessions section
  and the cache-read table: the totals sit in this table's total row, the
  session counts in the subagent rows and the project footnote, and the
  cache-read share in one sentence under this table.

A second page, `/value`, linked from the controls, shows what each
subscription buys. It opens with the pool and live-limit findings, the
block figure, and one ledger of each plan at its recent pace with what a
full 5-hour and weekly window holds, with a combined row. Each tool's
section then shows the drift tables with the main model and the
reference-rate cost, how much of each window was used, Codex credits,
estimated API cost by month against the plan price, and the runs that were
averaged (with their range and the last live reading). A closing section
says what the figures rest on: each tool's history and its live readings.

A panel with nothing to show says what to run (`scan`, `rebuild` for
labels) instead of staying blank. On a store of about 79,000 requests a page
renders in 110 to 260 ms. Everything is embedded in the page; it makes no
network requests and needs no Node toolchain. The visual system is written
down in [docs/design.md](docs/design.md).

## Public snapshot

```sh
usage-habit-report snapshot --out /tmp/usage-public
usage-habit-report snapshot --out /tmp/usage-public-12w --window 12w
```

Exports the dashboard from the store read-only, without scanning, pricing,
or network access. The default writes `index.html` for 4 weeks,
`index-1w.html`, `index-12w.html`, and `index-all.html`, plus three
tool-filtered versions of each, and `value.html`, the subscription value
page. Window, tool and page links use relative filenames and work from
`file://`. Each document embeds the same CSS, JavaScript, templates, and
queries as `serve`. With `--window 1w|4w|12w|all`, only that window and its tool
variants are written, with the all-tools page at `index.html`.

Project names become `project A`, `project B`, and so on, ordered by
all-time estimated cost, then path for ties. One mapping covers every window
and tool in a run. Paths, session titles, session and T3 thread ids, cwd,
T3 titles, and per-request rows are absent. Session tables retain the tool,
project pseudonym, elapsed time, request count, and estimated cost. The
heaviest fan-outs list becomes an omission note; its panel's aggregate
figures remain.

To keep public GitHub repository names and links, add exact stored project paths
to `[public_projects]` in the application `config.toml`:

```toml
[public_projects]
"/home/demo/git_repos/t3code-dev" = "https://github.com/demo/t3code"
"/home/demo/git_repos/t3code-other" = "https://github.com/demo/t3code"
```

The public display name is the last URL segment. Paths never appear in the
export, and paths sharing a URL remain separate rows. Other projects keep
pseudonyms. Malformed entries warn on stderr and are ignored. Only HTTPS
GitHub repository URLs are accepted. The local dashboard is unchanged.
Use `USAGE_HABIT_REPORT_CONFIG=/path/to/temporary.toml` with `--db` to review
an export using a separate config and store.

and activity-map readouts. Rounded rows may not add up. Real dates, local
hours, tool and model names, task labels, token counts, and other aggregate
figures stay. A note states the generation date and window; the footer keeps
the data-load time. Pseudonyms are stable within one run and may change in

### Automatic publishing

```sh
usage-habit-report publish [--no-push] [--out DIR] [--no-scan]
```

`publish` runs the same catch-up as `query`: scan, enrich, headline refresh,
and pricing. `--no-scan` exports the existing store. It writes all 16 pages
into a temporary sibling directory and checks every file for private store
values, both raw and HTML-escaped. The guard checks paths, session and T3
thread ids, titles of at least 12 characters, and the home directory. A guard
failure leaves the previous export untouched and runs no git commands.
After the guard passes, the new pages replace the destination, including stale files.

Set the destination in `~/.config/usage-habit-report/config.toml`:

```toml
[publish]
dir = "/home/demo/git_repos/design/usage-habit-report/site"
push = true
```

Paths use the same quoted scalar syntax as `[sources]`, including `~/`
expansion. `push` accepts `true` or `false` and defaults to `true`.
`--out` overrides `dir`; without either destination, `publish` fails.

When `dir` is configured, `serve` publishes before binding its port.
`serve --no-publish` skips this step. Without a publish destination, `serve`
behaves as before. Publish errors print a warning on stderr and the dashboard
still starts. The server opens the store read-only after the startup step.

Inside a git repository, `publish` stages only the destination and commits
changes with `Refresh the public usage snapshot`. It refuses to commit if
there are already staged changes. Repeating an unchanged export makes no
commit; changes in generation time and page-load timing alone do not count. Outside a repository,
it only writes the files.

Before pushing, it checks `git log @{u}..HEAD --format=%s`. Every unpushed
commit must have the snapshot commit message. If other commits exist, it
keeps the snapshot commit locally and reports the count of other commits.
`--no-push` or `push = false` always disables pushing. Git failures, including
a missing upstream or a network error, fail the standalone command.
The summary reports the file count, commit result, and push result or reason.

GitHub Pages copies `usage-habit-report/site/` to `/usage/`; the flight visualizer is at `/map/`.
The deploy workflow uses committed HTML and does not build Rust. The checked-in
placeholder says that no snapshot has been generated yet.

## Codex ingest

- Source: every `rollout-*.jsonl` and `rollout-*.jsonl.zst` under
  `~/.codex/sessions/` (dated `YYYY/MM/DD/` folders) and
  `~/.codex/archived_sessions/` (flat). `--codex-dir` (or `CODEX_HOME`) points
  at a different Codex home. Codex zstd-compresses older rollouts; for those,
  offsets and `bytes read` count decompressed bytes. An unchanged `.zst`
  (same size and mtime) is skipped without being decompressed.
- A rollout that is compressed in place or moved to `archived_sessions/` is
  recognised by its file name minus the `.jsonl[.zst]` suffix. The new path
  takes over the old source row and its offset, so nothing is counted twice.
  If two copies are on disk at once, the tracked one (else the plain one) is
  read and the other is skipped.
- Session id is `session_meta.id` from the file's first record. A long session
  can span several files (`rollout-<time>-<id>_<window>.jsonl`); they all
  attach to session `<id>`. `cwd` comes from `session_meta.cwd`.
- Model and effort come from the latest `turn_context` record (`model`,
  `effort`). `session_meta` carries no model. Requests before any
  `turn_context` get a null model; no default is filled in.
- Requests, newer format: one per `token_usage_record` (one per model
  response), keyed by its `response_id`. Older rollouts lack these records;
  then requests come from `event_msg` / `token_count` records, keyed
  `<file stem>#<ordinal>`. Once a file has a `token_usage_record`, its later
  `token_count` records only update the running total.
- `token_count` carries the cumulative `total_token_usage` and the latest
  call's `last_token_usage`. A request is recorded each time the cumulative
  total changes, and its counts are `last_token_usage`. On real data the two
  agree on 46,651 of 46,665 changes. They disagree when the counter restarts
  (it goes down) or jumps forward (seen after a user fork). There the
  cumulative delta is wrong and `last_token_usage` is right. A `token_count` whose total
  did not change repeats the previous one and is skipped. The newer
  per-response records are preferred because about 0.4% of responses get a
  `token_count` whose total never moved (`last_token_usage` all zero); the
  `token_count` path loses those.
- Token columns: Codex's `input_tokens` includes cached input, so
  `input_tokens` = `input_tokens − cached_input_tokens − cache_write_input_tokens`,
  `cache_read_input_tokens` = `cached_input_tokens`,
  `cache_creation_input_tokens` = `cache_write_input_tokens` (always 0 so
  far), `output_tokens` = `output_tokens`, and `reasoning_tokens` =
  `reasoning_output_tokens` (part of the output, not on top of it). If cached
  exceeds raw input, uncached input is clamped to 0 and counted.
- User turns are `response_item` messages with `role: "user"`, unless every
  text block is harness-injected. Injected blocks start with
  `# AGENTS.md instructions` or one of these tags: `<environment_context>`,
  `<user_instructions>`, `<recommended_plugins>`, `<skill>`,
  `<external_codex_apps_open_page>`, `<turn_aborted>`,
  `<send_user_message_question_reply>`, `<codex_delegation>`,
  `<realtime_delegation>`, `<heartbeat>`, `<in-app-browser-context>`,
  `<subagent_notification>`, `<codex_internal_context>`,
  `<guardian_tool_descriptions>`, `<user_shell_command>`, `<image>`.
  Sessions driven only by delegation (voice, or threads an agent created)
  therefore have 0 turns and no title.
- Title: first line of the first typed block. Codex Desktop wraps prompts in
  IDE context (`# Files mentioned by the user`, `# Files pasted by ...`,
  `# Selected text`); the title is the text after the `## My request...` line,
  and none if that is empty.
- Subagents: `session_meta.parent_thread_id` is the parent session id, and
  `source.subagent` the kind. `is_subagent = 1` when either is present (or
  `thread_source` is `subagent`). `agent_type` is `guardian` for internal approval
  subagents (`{"other": "guardian"}`), which are excluded at ingest. Spawned
  agents have `thread_spawn` or their `agent_role` when Codex records one.
  `session_meta.session_id` is the root session; it is not stored.
- Forks (`forked_from_id` set, which includes most spawned subagents) begin
  with a copy of the parent's history, including its `token_count` records.
  Records with `ordinal` below `subagent_history_start_ordinal` are that copy;
  for forks without that field, records within 1 s of the first record are.
  The copy sets the running total and model, and adds no requests or turns.
  A user fork (no parent) is a top-level session with null
  `parent_session_id`.
- Parser state between scans (running total, model, effort, fork cut) is kept
  per source in `codex_cursors`.

## Antigravity ingest

- Sources: every `*.db` in `~/.gemini/antigravity/conversations` (native
  app) and in `~/.t3/userdata/providers/antigravity/*/antigravity-acp/conversations`
  and the same path under `~/.t3-personal` (T3 bridge). `--antigravity-dir` (repeatable) replaces both. The session id
  is the file stem, which is the conversation id.
- Each database is opened read-only (`mode=ro`). If the WAL/SHM sidecars
  block that, it is opened with `immutable=1`, which ignores the WAL, and
  `scan` reports the count. Nothing is ever written to these databases.
- Requests are generation steps (`step_type` 15) that carry a usage message
  (metadata field 9). The key is `<conversation-id>:<step idx>`. Field 9.2 is
  `input_tokens` (uncached), 9.5 is `cache_read_input_tokens`, 9.3 is
  `output_tokens` (includes thinking), and 9.9 is `reasoning_tokens`.
  Antigravity reports no cache writes, so `cache_creation_input_tokens` is 0.
  The timestamp is the generation start (field 6). Generation steps without
  usage (cancelled or still running) are skipped and picked up once they
  finish.
- Model: the `gen_metadata` row for the same generation, matched by bot id
  (native) or by identical usage bytes (T3), gives the model name (for
  example `gemini-3.8-flash`). When the step's selected model (field 24.8,
  for example `gemini-3.8-flash-high`) extends that name, the suffix is stored
  as `effort`. Without a matching row the selected model is used. Both count
  as `measured`. A generation that names no model gets the database's first
  known model and the session's `model_source` becomes `guessed`. With no
  model anywhere, `model` and `model_source` are null.
- Teamwork child conversations are separate databases. The parent id comes
  from `parent_references`, else field 5 of `trajectory_metadata_blob`. The
  child gets `is_subagent = 1`, `parent_session_id`, and `agent_type` (the
  agent name, field 4.1). Each generation lives in exactly one database, so
  nothing is counted twice. Parent versus child totals for a run:

  ```sql
  SELECT r.is_subagent, SUM(r.output_tokens)
  FROM requests r JOIN sessions s USING (tool, session_id)
  WHERE r.tool = 'antigravity'
    AND (s.session_id = :run OR s.parent_session_id = :run)
  GROUP BY r.is_subagent;
  ```

- Title: the first non-empty line (up to 120 characters) of the first user
  prompt (`step_type` 14). `cwd` comes from the T3 bridge's `<id>.meta`
  (`cwd` or `allowed_tools_workspace`), else the native workspace URI in
  `trajectory_metadata_blob` field 7.
- Incremental: the source row stores the combined size and latest mtime of
  the database and its `-wal` file. When both match, the database is not
  opened. Otherwise every step is read again, because SQLite rewrites rows in
  place; requests merge by key. `offset` holds the next unseen step idx, so
  only prompts at or past it add to `user_turns`. A database whose steps fall
  below `offset` is reset and re-read.

## Task labels

Every top-level session gets one label at ingest, picked from its opening
user prompt by deterministic keyword rules in `src/labels.rs`: `research`,
`coding`, `debugging`, `writing`, `review`, `data-analysis`, `ops-config`, or
`other`.

- The ingester classifies the prompt while it holds it in memory and writes
  only the label (`sessions.label`, `sessions.label_source = 'rule'`). The
  prompt text is not stored; the title is still its first line.
- A root session (top-level, or a subagent whose parent is unknown) whose
  opening prompt never reached the log (no user
  turn, or logs ingested before labels existed) is classified from its
  headline instead, once the headline refresh has one, under
  `label_source = 'headline'`. A hand-set label still wins.
- Subagent sessions report under their root session's label, following
  parent links across harnesses (an Antigravity subagent started from a
  Claude Code thread counts under that thread's label).
- Rules are an ordered list of (label, word-start stems, whole words). The
  rules run over the opening line first; if none matches, over the first 600
  characters. The first rule that matches wins, so specific intents
  (`debugging`, `review`, `ops-config`) come before the broad `coding` rule.
  A prompt that matches nothing is `other`.
- A session is labelled once, from its first typed prompt. Re-reading a file
  that shrank derives the label again.
- A hand-set label (`label` command) is in `session_labels` and is preferred
  over `sessions.label` by every query.
- Subagent sessions have no label of their own. Queries give them the label
  of their root session at read time.
- A session with no typed prompt (for example, one that holds only injected
  context) has no label and is reported as `unlabelled`, as are sessions
  ingested before schema v5 until their logs are read again.

The rules are keyword matches, not a model. Expect some misfiles; correct
them with `label`.

## MCP server

```sh
usage-habit-report mcp
```

Runs a stdio MCP server (JSON-RPC 2.0, one message per line). Stdout carries
protocol messages only; logs go to stderr. Each tool calls the same Rust
function as the matching `query` command and returns its `--json` body as a
single text content block (compact, not pretty-printed), so the shapes in
[docs/json-shapes.md](docs/json-shapes.md) apply unchanged. Calls with the
`2026-07-28` revision's `_meta` also get the body as `structuredContent`.

| Tool | Arguments | Same as |
|------|-----------|---------|
| `usage_summary` | `since?`, `group_by?` (`tool-model` or `label`) | `query summary` |
| `usage_session` | `key`, `rows?`, `since?` | `query session` |
| `usage_project` | `key`, `since?` | `query project` |
| `usage_projects` | `since?` | `query projects` |
| `usage_models` | none | `query models` |
| `usage_agents` | `since?` | `query agents` |
| `usage_labels` | none | `query labels` |
| `usage_value` | none | `query value` |

`since` is `12h`, `7d` or `2w`. `usage_session` takes a session id, a unique
prefix, or a T3 thread id; `usage_project` takes a path or folder name. An
ambiguous key returns an error result (`isError: true`) whose text is the CLI's
body, `{"error": "ambiguous", "key": ..., "candidates": [...]}`; no match
returns `{"error": "not found", "key": ...}`. Bad arguments are error results
too; an unknown tool name is a JSON-RPC error (-32602).

Every tool description says: output never contains prompt or response text
(only session and T3 thread titles); dollar figures are estimates; the first
call may run a catch-up scan that can take up to 30 s on a cold store.

**Catch-up rule.** Nothing runs at startup, so `initialize` answers at once.
The first tool call runs the same catch-up as `query` (scan, enrich, price).
A later call repeats it only when more than 60 s have passed since the
previous catch-up finished. Global `--no-scan` turns it off for the whole
session; `--offline` and `--db` work as for the CLI. Requests are handled one
at a time, so a call that arrives during a scan waits for it.

**Protocol.** `initialize` echoes the client's version when it is one of
`2025-11-25`, `2025-06-18`, `2025-03-26` or `2024-11-05`, and otherwise offers
`2025-11-25`. The server also answers `server/discover` and per-request
`_meta` version checks from the `2026-07-28` revision, which modelcontextprotocol.io
lists as current; that path is tested here but not against a real client.

## Active time

`active_seconds` merges every recorded event in a session with all linked child
session timelines, then subtracts gaps longer than 15 minutes. A gap of exactly
15 minutes remains active. Antigravity steps include their recorded start/end
interval; Claude Code and Codex events are timestamp points. An isolated point
contributes zero time. Codex copied fork history is excluded from active time.
`elapsed_seconds` keeps the wall span. `idle_gap_seconds` reports the threshold.

Project and per-tool active totals sum top-level sessions only. Linked children
report their own active time but are covered by their parent in totals. Children
with no linked parent count separately; the multi-agent panel reports their count
per tool. Session and project time covers whole sessions selected by the window,
while requests and costs still cover requests inside the window.

Ingest stores timestamp-only intervals in `session_events` and caches the merged
duration in `sessions.active_ms`. Every changed session recomputes its ancestors
inside the same transaction, including when a child is read after its parent.
Queries and the read-only dashboard never reread transcripts or compute gaps.
The v6 migration preserves usage and manual labels and rewinds source cursors
once, so the next scan can backfill non-request event timestamps. Sessions whose
logs are no longer present keep a null active time and contribute zero to time
totals. Run `rebuild` to discard usage whose source logs have been deleted.

## Store schema (v11)

The schema version is kept in `PRAGMA user_version`; migrations live in
`src/store.rs`.

- `sources`: one row per log file, with `path`, `offset` (bytes consumed;
  for Antigravity, the next unseen step idx), `size`, `mtime_ms`, and
  `scanned_at`.
- `sessions`: one row per `(tool, session_id)`, with `is_subagent`,
  `parent_session_id`, `agent_type`, `title`, `cwd`, `started_at_ms`,
  `ended_at_ms`, `user_turns`, `model_source` (Antigravity:
  `measured` or `guessed`), and `label` / `label_source` (the rule result,
  see [Task labels](#task-labels)). `project`, `project_name` (v4),
  `t3_thread_id`, and `t3_title` are filled by the enrich step (see
  [Projects and T3](#projects-and-t3)).
- `requests`: one row per `(tool, request_key)`, with `session_id`,
  `is_subagent`, `source_id`, `ts_ms`, `model`, `effort`, and the four token
  counts. `reasoning_tokens` is filled where the harness reports it (Codex,
  Antigravity; null for Claude Code). `canonical_model` and `cost_usd` are
  filled by the price step and stay null for unpriced models.
- `codex_cursors` (v2): one row per Codex source, `state` = JSON parser state
  carried between incremental scans.
- Trigger `requests_unprice` (v3, ticket 04): clears `canonical_model` and
  `cost_usd` when a row's model or token counts change.
- v4 (ticket 05): `sessions.project_name`, and indexes on `sessions.project`
  and `sessions.t3_thread_id`.
- v6 (ticket 13): `sessions.active_ms` and `session_events`, timestamp-only
  intervals keyed by source and session for incremental tree recomputation.
- `session_labels` (v5, ticket 06): `(tool, session_id)` primary key, `label`,
  `set_at` (epoch ms). Hand-set labels; independent of the raw-log rows.
- `limit_samples` (v10): one row per `(tool, source_id, ts_ms, window)` with
  `used_percent`, `resets_at_ms`, and `kind` (`reading` from Codex
  `rate_limits`, `rejected` from Claude Code refusals). Feeds `query value`.
  The migration re-reads Codex and Claude Code sources from byte 0.
- v11: `limit_samples.credits_balance` (the Codex credit balance at each
  reading; the migration re-reads Codex sources once), and `live_limits`, one
  row per `(tool, pool, window, ts_ms)` with `used_percent` and
  `resets_at_ms`, written by `limits record`. `pool` is empty for the plan's
  own windows. `rebuild` keeps this table.
